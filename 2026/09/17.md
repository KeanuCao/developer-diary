## ☢ Test Harmlessness（测试无害性）—— 资质性硬要求

> **先过无害性，再谈可复现性。** 一条用例即使「步骤」栏完美可复现、判据精确到字节，只要带有**不受控的业务副作用**，它就是**不合
格交付**——等同「未验收」，必须返工。
> 本条不接受「注意一下」「尽量」这类软化措辞，也不接受「测试环境嘛，坏了重建就行」。
> **口径来源**：用户 2026-09-17 明确要求 ——「对于 database 的操作一定是慎重的，**即使是测试环境**」，并把 Test Harmlessness 定为
 qa-engineer 的核心要求。

**一句话判据**：**测试跑完之后，被测环境必须与跑之前一致**。唯一允许的差异，是「本次用例自建、且已在用例内销毁」的一次性对象。

### 1. 作用域规则：写操作只允许落在「自建的一次性对象」上

- 需要写操作时，**必须先把作用域收敛到本次用例自建的一次性对象**：独立库 / 独立 schema / 独立目录 / 独立卷 / 容器内 `/tmp`，并在
用例内销毁。
  - ✅ `CREATE DATABASE nexus_tc00_probe` → 补丁只跑在这个库里 → `DROP DATABASE … WITH (FORCE)`；补丁目录用 `NEXUS_PATCH_DIR` 指
向容器内 `/tmp/...`
  - ❌ 在真实业务库里「顺便」建个业务之外的表来验证
- **绝对禁止对业务对象做任何写操作**：`DROP` / `TRUNCATE` / `DELETE` / `ALTER` / `UPDATE` 业务表或业务库 —— **即使它「能靠重跑补
丁恢复」、即使这是测试环境**。
  可恢复 ≠ 无害：中途失败留下的是半个环境，要靠人工修 —— 而「需要人工修」本身就是伤害。
- **绝对禁止改动已应用的历史补丁文件**（哪怕随后 `git checkout` 改回）。已发布补丁是只读契约，「临时改一下」就是把它变成可变状态
。
- **绝对禁止往正式目录里塞测试文件**：`db-patch/`、`scripts/`、`docker-compose/` 这类被**生产链路消费**的目录。测试文件只能待在
一次性目录里。
- 造负路径优先选**可逆注入**，且注入点本身也要是一次性对象。

### 2. 有副作用的用例必须自带三样东西（缺一样即不合格）

1. **作用域声明**：写什么、写在哪、**为什么非写不可** —— 说不出「非写不可」的，直接改成无害写法。
2. **幂等清理步骤**：写在「步骤」栏里（不是塞进备注），可重跑、可在失败后重跑。
3. **无害性自证**：跑前 / 跑后各取一次**指纹**并断言一致（真实库的行数、表清单、`max(file_name)`；宿主仓库 `git status --porcela
in` 干净）。
   —— **自证，而不是「我保证跑完是干净的」。**

### 3. 落笔前自问三句（答不上来就不许写进 TC）

- **「这条用例执行到一半被 Ctrl-C，环境会怎样？」** —— 答案不能是「要人工修」或「看情况」。
- **「这条用例失败后，下一条用例 / 下一次 `up.sh` 还跑得起来吗？」**
- **「我写进去的这份状态，有没有**别的东西**在消费它？」** —— 活教材：`t_db_patch` 的 `max(file_name)` 是乱序保护的基准，往里写
一条探针记录，就能让后续**真实**补丁全部 `exit 3`（详见下方 4 的来历）。

### 4. 做不到无害怎么办

先**改设计**（换隔离维度：换库 → 换 schema → 换目录 → 换容器）→ 仍然做不到，就把它列为「**不做**」，写清原因与风险。
**绝不降低标准照做**，也绝不把「有副作用的用例」偷偷混进用例表。
