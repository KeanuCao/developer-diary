## 安全问题
 - 我碰到这个菜单，有意思
 ```
 We're changing auto mode to no longer charge for classifier requests in Claude Code.

  However, this session isn't eligible because your requests go through api.deepseek.com, which isn't compatible with this update.

  Nothing breaks: auto mode keeps working, and its classifier requests are billed as before.
 ```
 - DeepSeek了一下
 ```
 Claude Code 的自动模式（auto mode）中，有一个安全分类器会在执行 shell 命令、网络请求等操作前做安全检查。过去这个分类器在客户端运行，每次工具调用会额外消耗少量 token，这部分开销由用户承担。Anthropic 现在把分类器迁移到了服务端，服务端执行检查时不再向用户收取分类器开销。

但服务端分类器依赖 Claude Code 与 API 之间的一套特定字段传递机制：请求中要携带 safeguards 字段，响应中要返回 safeguard_results 字段。你当前通过 api.deepseek.com 接入，而这个 API 端点没有实现这套字段的透传，服务端的检查请求无法到达你的会话。因此 Claude Code 只能回退到本地分类器，而本地分类器的请求仍然按旧方式计费。
 ```

## RAG
今天本来就想搞明白 RAG 到底咋回事，结果一聊聊了一大堆，从 PDF 怎么读一直扯到召回率、索引、甚至一个人要不要搞评估集。现在脑子有点涨，但趁还没忘，赶紧写点。

一开始我以为 RAG 就是让大模型读文件回答问题。后来才反应过来，大模型根本不直接读整个 PDF。它就是个最后答题的，前面得有人把 PDF 拆开、洗干净、切好、变成向量，再去库里捞相关内容，最后才轮到它说话。说白了，大模型是厨子，前面择菜洗菜切菜的全是工程活。

Tika 今天被我折腾了半天。它就是个拆箱工，啥格式都能拆，拆出来文本、Markdown、元数据、附件。但拆出来是毛坯，不是净菜。Tika 4.0.0 默认输出 Markdown，但 tika-app 4.x 居然不是单 jar，得解压。输出还默认往终端吐，不支持直接指定文件。我一开始搞出一堆乱码，怀疑 PDF 有问题，结果用 pdftotext 一试，PDF 好得很。那就是 Tika 或者终端编码的锅。最后用 Pipes 模式加 `--content-only`，总算弄出干净的 md 文件。这种小坑真的烦，但踩过一次就记住了。

不过今天聊 Tika 的时候有个点我觉得挺有意思，就是它自带的 OCR 其实不算强，默认走的是 Tesseract，但它是可以外接别的 OCR 引擎的。比如飞桨的 PaddleOCR，中文识别效果就很好。思路是自定义一个 Tika 的 Parser，检测到需要 OCR 的图片或者扫描页，就调自己的 OCR 逻辑，把结果塞回去。Java 这边已经有人把 PaddleOCR 的模型转成 ONNX，封装成纯 Java 库，Maven 引一下就能本地跑，不用 Python 环境。也有基于 DJL 的 SmartJavaAI，支持 PP-OCRv5，还有 Python 服务化 + gRPC 的方案，精度最高但要运维。感觉这个扩展点挺关键的，因为扫描件和图片型 PDF 在企业里太常见了，Tika 自己搞不定的话，外接一个强 OCR 就能补上这块短板。以后要是真遇到扫描件，我肯定得回来试试这个。

清洗这事，白话就是择菜洗菜去烂叶子。页眉页脚、断行、全半角、OCR 错字，都得弄掉。有专业库，但单人玩，Tika 加正则差不多够了，别一上来就上重武器。

切块聊得最久。结构感知切块有点意思，按 Markdown 标题层级切，把标题路径当元数据留着，表格列表单独处理。大模型切块听起来聪明，但又慢又贵还不稳定，还可能把原文改了，不划算。企业里切块工作量巨大，因为每家文档风格都不一样，还得做模板。但我一个人，按标题切就完了，别想太多。

Embedding 就是把文字变成坐标，意思近的坐标就靠近。不用本地部署大模型，调 API 最省事。向量库就是存向量、原文、元数据。pgvector 是 PostgreSQL 的扩展，不是独立数据库。索引这块有个不可能三角：速度、召回率、内存成本，三个不能同时拉满。上游解析清洗切块向量化决定上限，索引决定你多快多贵去接近那个上限。

召回率今天也终于搞懂了，就是该找的东西你找出来多少。测试要人工标注，确实麻烦。企业里得有人长期管，但不一定全职。我一个人玩，自己造 5 个知道答案的问题，手动看看答案和引用对不对，就得了。别搞 RAGAS，别搞标注集，别把自己变成全职标注员。

脚手架也聊了，Dify、LangChain4j、Spring AI 一堆。一个人玩，核心就是能跑通大于完美。别上 Milvus，别做权限多租户，别本地部署 Embedding 大模型。先跑通再说。

今天没聊完，pgvector 实战、重排、上下文组装、生成评估都还欠着。但主线清楚了：RAG 不是模型问题，是数据工程问题。明天要是有空，就从那个 Markdown 开始，切块、入库、问几个问题。先让它跑起来，别的以后再说。
