# 标题：如何设计一道让顶尖大模型“抓狂”的 Terminal 实战题？

最近，我参与了一个专门评测大模型（LLM）代码与终端排障能力的项目。这个项目的核心目标很有意思：**剥去大模型“生成代码”的华丽外衣，把它们扔进一个真实的、甚至有点脏的 Linux 终端里，看看它们到底能不能像真正的全栈工程师那样干活。**

项目的要求很严格：必须基于真实工作场景，严禁用 AI 生成虚假的“完美代码”。

作为一个老后端，我脑子里立刻冒出了一些 2016 年曾把我折磨得死去活来的真实产线事故。经过几天的拆解和重构，我把当年的“噩梦”变成了一道极具挑战性的评测题。

今天不谈具体的代码实现，只聊聊我在设计这道题时的几个核心思路，以及我是如何给顶尖大模型“挖坑”的。

### 1. 拒绝“上帝视角”：把线索藏在沙盒里

现在的 AI 习惯了做“单选题”。如果你告诉它“系统报了空指针，因为参数传错了，请修复”，它能秒出答案。

所以我出题的第一原则是：**绝不给明确提示**。

我在题面里只交代了最表面的业务现象：“系统升级后，用户提交的表单数据神秘消失了，没有任何报错”。
至于为什么消失？我不告诉它。我把真正的线索（比如服务器环境变更日志、某个隐蔽的环境变量配置）藏在了庞大的沙盒目录深处。模型必须像真正的 SRE 一样，在终端里用 `ls`、`find`、`grep` 一点点去翻找，结合上下文推理，才能拼凑出真相。

### 2. 制造“静默失败”：没有报错的 Bug 才是最可怕的

在真实世界里，最恶心的 Bug 往往不是满屏飘红的 `Exception`，而是系统静默地吞掉了错误。

在题目的代码环境里，我特意还原了老一辈程序员为了“系统稳定性”写下的极其宽泛的 `try-catch`。它会拦截致命的底层异常，只在日志里轻描淡写地打印一句 `WARN`。

大模型极度依赖清晰的控制台报错堆栈来逆向推导。一旦拿不到 `Stack Trace`，它极大概率会陷入幻觉，去乱改配置文件，或者在无关的业务代码里反复打转，最终在终端里彻底迷失。

### 3. 跨栈的“连环套”：别想靠改一个文件通关

很多模型擅长写单文件脚本，所以我给它上了一个完整的 Web 全栈架构（前端模板 + 拦截器 + 控制器 + 底层持久化）。

我还特意加入了原生的安全防护机制。这意味着模型不能随便发个 `curl` 请求就去测试接口，它必须理解 HTTP 协议，自己抓取安全凭证（Token），带上 Session，才能模拟出真实的浏览器行为。如果它为了图省事，把安全防护删了，评测脚本会直接判它不合格。

### 4. 伪装的迷阵：用“祖传代码”增加认知负荷

真实的工程代码从来不是干干净净的。

我在工程里加入了一些无用的历史依赖、复杂的类继承关系，甚至在底层框架的配置上做了一些古老的处理。当模型深陷在这些错综复杂的依赖树和继承链中时，它的注意力会被严重分散。只有抛开那些“噪音”，它才能真正定位到那最核心的、只需改动一两行的根因代码。

### 5. 刚性的判卷：用真实的物理世界说话

既然考的是全栈排障，就不能靠模型自己说“我修好了”。

我设计的自动化验证脚本（Verifier）非常“冷血”。它不看模型改了哪些代码，也不管代码风格优不优雅。它只做两件事：
1. 伪装成真实用户，发起端到端的 HTTP 请求。
2. 直连数据库，查最终落库的数据对不对。

如果数据没写进数据库，无论模型在终端里怎么吹嘘，最后都是 0 分。

### 写在最后

做完这道题，我最大的感触是：**当前的大模型就像是个“刚背完整本百科全书的天才实习生”。** 

它们对语法的熟练度远超常人，但它们缺乏在混沌环境中“抽丝剥茧”的系统直觉。它们找不到那份被藏在系统角落的变更日志，也不理解为什么有人会写出吞异常的垃圾代码，更想不到几十年前的一个底层反射机制的变更，会在今天引发一场没有报错的灾难。

这道题已经提交了。如果有一天，大模型能在没有任何人类提示的情况下，纯靠终端命令排查出当年的那个“坑”，那我这个老后端，可能真的要考虑让位了。不过至少现在，在真实的屎山代码面前，人类的工程经验依然有着不可替代的价值。
